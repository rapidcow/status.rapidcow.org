  Frankly, this isn't exactly the same as accessing through
  status.rapidcow.org *with* the domain name (I believe
  somewhere in the SSL handshake the client sends the domain
  name so the server would return the correct certificate --
  which was the reason I was able to host multiple domains yet
  have separate SSLs sent back for each), but if we assume the
  underlying HTTP server just looks at the Host header in the
  HTTP request I send (judging by my other site hosted on
  Codeberg Pages this seems to be the case), suffice it to say
  that I have reliably produced what would have happened *if*
  I switched back to Codeberg now.  Plus playing with the
  DNS record just for this experiment would be too silly, so
  reasonably I decided not to....   but instead play this
  trick to get around the mismatching SSL certificate name
  (FYI, subdomain certificates with a CN entry like what I got
  above with "CN=*.codeberg.page" are only one-level deep,
  so an Internet-standard abiding client would deem it invalid
  -- see third section of RFC2818 for reference.  On the other
  hand, s_client is just an SSL client, so it doesn't validate
  that consistency, and I can still send an HTTP request in
  spite of all that. :)

  So that is the state of Codeberg Pages now... I couldn't

  think I will. :(  But maybe stepping away is a good thing:

  shouldn't asking them to look into this minute problem...

  But back to the server.  Something went morbidly wrong when
  I tried to install ubuntu-desktop on the server last night
  (I wanted to see how this "X11 forwarding" thing I've heard
  worked over SSH... for no good reason u_u):  The server
  stopped connecting to the Internet.  I couldn't install or
  update with `apt-get', I couldn't `ping(1)' any domain (heck
  they wouldn't even resolve in the first place) -- but worst
  of all...  I couldn't log into it from my laptop via SSH.
  This meant that in the past few hours I had been using the
  Web console provided by Digital Ocean (the so-called "Rescue
  console", but that's only because the other console hang
  since the server was basically offline and the rescue console
  is the console that interacts with the server on the private
  network locally).

  Now, know that I'm not saying that the server files got
  corrupted.  It was purely a network problem which *may* have
  been caused by ubuntu-desktop (or the x2goserver I installed
  shortly after) was bringing its own network manager that was
  conflicting with the then network manager.
  The solution was almost trivial though: to get the Internet
  to work I only had to hook the eth0 interface to its gateway
  and subnet mask, like this:

  ifconfig eth0 <ipv4 address> netmask <subnet mask> up
  ip route add default via <gateway address>

  The IPv4 address here is indeed the public 164.90.136.30
  that you already know.  These are commands were all it took
  to bring my server back on the Internet.  And I did not have
  to edit /etc/resolv.conf to use Google's DNS server (8.8.8.8)
  because Digital Ocean's DNS servers work just fine (plus, not
  a lot of posts I've seen mention this, but chances are you're
  not supposed to edit /etc/resolv.conf directly?... mine was a
  symlink to a file deeply nestled inside /run/ and had a huge
  block of comment at the top telling me to not edit it.)
  But I just couldn't for the life of me figure out how to
  tell it to configure those *on boot* -- as soon as I reboot
  all of that had to be re-run; and since SSH is busted without
