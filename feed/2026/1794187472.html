  Anyways, for the longest time, the whole site (with
  its STAGGERING amount of... 4 files) was just built
  from scratch, every time.  feed.html globs the data/
  directory (where I keep said text files), sorts them
  by date, and includes one's content.  (feed.xml does
  the same except it only looks for specific headers.)
  This is just a dumb source translation, meaning one
  input file (the Template Toolkit file with the loop)
  to one output file (feed.html and feed.xml).  To do
  the same for 47 files (at the time of writing this)
  would mean 47 sources (!) for each standalone perma-
  link, which obviously had to be done differently...

  (But okay, this bit isn't the hard part... you could
  just, have an actual generic template with substitutable
  variables.  I was just... lazy to write one :P)

  So I want dependency graph... but I also don't want
  magic (black-box in other words, like most SSGs are).
  But I also want the comfort of not having to worry
  about things most of the time.  You want to know how
  I did it?  Make! or any build system that works on files
  really.  What I made was essentially a build script
  generator that takes repetitive part out (like writing
  the file names twice; the `a/%: b/%' that I have used
  extensively for GNU make).  (I wrote it up during the
  summer in my grandparents' house for my archive project
  site (www-cellar), inspired by FreeBSD ports I'd been
  seeing on my T480 (it's a whole-ass language written in
  Make!  I'm not saying GNU Make isn't, but you just can't
  deny that the `bsd.*.mk' headers aren't totally wack.)
  The other thing I borrowed from FreeBSD are the /etc/rc.d
  PROVIDE + REQUIRE headers read by rcorder(8), except I
  renamed them as HAVE + NEED.)

  To generalize it to my other sites (including this one)
  though, I had Claude Code extract the shared bits into
  a Perl module.  So I know, I know, siteconf looks vibe-
  coded, and it *is*... but it's just the execution and not
  the idea! >:O  And I've accepted that if you want to make
  something so niche and you need right away, AI is the only
  realistic way to do it without having me completely give
  up on college and spend every hour awake to write this.
  (But okay, on that... I am not getting into that here. =_=)

  The part I didn't like about GNU make was globbing
  (which I guess the creator of Ninja also noticed and
  intentionally left out of their build script DSL.)  But,
  to put it simply, I think globbing is an anti-pattern
  because if your site loses some posts, you wouldn't know.
  (The MANIFEST is taken straight from Perl EU:MM, which
  I like more than how Python and other packagers do it,
  since I have a clear list of files I can expect to see.
  (Java is cool though!  They have META-INF/MANIFEST.MF :)
  )  This also helps with deterministic builds, which is
  something I care deeply about: to be able to know that
  my web site is self-archiving and not something that
  needs saving with an external archive system ten years
  from now.  (Of course the checksum on sources and the
  build outputs and version pinning of the environment will
  have to be done separately, but the stability of input /
  output rules won't be a separate concern. ;)

  But back to this: dependency graph is solved; what's
  left is just convenience.  For that, I just had Claude
  Code write a source-generator that updates the list of
  dependencies (the text files NEEDed by a year-feed,

  didn't explicitly tell Claude to do that, but it's what
  I would have done too.  I explicitly expected that
  siteconf would fit in a larger system where its input
